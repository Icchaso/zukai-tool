# 図解ジェネレーター

どんなトピックでも、予備知識ゼロの読者が読んで腹落ちする「図解Webページ（HTML）」を生成し、そのまま surge.sh に公開して共有URLを発行するスキル。

品質のゴールは「その分野を知らない人が、図の順番を追うだけで仕組みを理解できること」。このゴール自体はページには書かない。

## 参照ファイル

| ファイル | 役割 |
|---|---|
| `references/base.html` | 図解の「額縁」。Tailwind CSS CDN・Lucide Icons・配色トークン定義済み。中身だけ差し替えて使う |
| `references/model-answer.html` | 完成品の見本。デザインの密度・色使い・図の組み方はここから読み取る |
| `references/audience.md` | 利用目的（自分用／提案用／社内共有用）ごとの構成方針 |
| `references/node-install-guide.md` | Node.js が無い環境での導入手順 |
| `scripts/deploy-diagram.sh` | 公開スクリプト（ランダムドメイン生成・robots.txt・履歴記録込み） |

## 手順

### 1. 準備 — 見本と額縁を頭に入れる

最初に `references/model-answer.html` を読み、完成品の水準を把握する（色・余白・カード・図の種類・情報量）。デザインルール集の代わりに、実物から読み取る方式。

次に `references/base.html` を読み、差し替えポイントを確認する:

- `<!-- TITLE -->` / `<!-- DESCRIPTION -->`
- `<!-- CONTENT_START -->` 〜 `<!-- CONTENT_END -->`
- 配色トークン（`zu-bg` `zu-surface` `zu-border` `zu-accent` `zu-text` `zu-muted` `zu-dim` `zu-positive` `zu-negative` `zu-warning`）

`base.html` が見つからない場合はフォルダ構成が壊れているので、その旨を伝えて中断する。

### 2. 利用目的を決める

`references/audience.md` の検出シグナルに照らして、この図解が **自分用／提案用／社内共有用** のどれかを判定する。添付素材からも推測する（顧客名があれば提案用、社内フローなら社内共有用など）。判定できないときだけユーザーに3択で確認する。

確定したら「◯◯用として作りますね」と一言伝えて進む。

### 3. リサーチ — 情報の鮮度に責任を持つ

ウェブ検索を2〜3回行い、学習データではなく検索結果を情報の正とする。観点は3つ:

1. **正式な定義**（公式ドキュメント・一次情報）
2. **最新動向**（直近の変更・現在のベストプラクティス）
3. **具体例**（たとえ話の材料になる実例・数字）

採用した情報には、必ず出典セットを控える: **ソース名 / URL / 発表日（公開日）/ 取得日（今日）**。発表日は必ず探しに行き、古い・不明なソースは新しいものに差し替える。図解の信頼性は情報の鮮度で決まる。

### 4. コンテンツを組む

audience.md の該当目的の「構成パターン」「成功基準」に従って章立てし、見本のデザイン水準で Tailwind クラスを使って自由にレイアウトする。守るべき原則は「内容づくりの原則」と「ビジュアルの型」（後述）。

### 5. ファイルに保存する

1. `output/` が無ければ作る
2. トピックの短い英語スラッグを決める（例: `api-basics`, `coffee-brew`）
3. `references/base.html` を `output/{スラッグ}.html` にコピーし、プレースホルダーを置換する
4. ローカルではブラウザで開かない（公開後にURLで確認する）

### 6. 公開する

まず Node.js を確認する:

```bash
node --version
```

無ければ `references/node-install-guide.md` の手順で導入を案内する（導入完了後にここへ戻る）。

**公開の実行**（macOS / Git Bash）:

```bash
bash .claude/skills/creating-visual-explainers/scripts/deploy-diagram.sh output/{スラッグ}.html {スラッグ}
```

**Windows PowerShell で bash が使えない場合**（surge はフォルダ単位でしか公開できないため、ファイルを直接渡すと `ENOTDIR` で失敗する。一時フォルダに `index.html` として置いてから公開する）:

```powershell
$t = Join-Path $env:TEMP ("zukai-" + (Get-Random)); New-Item -ItemType Directory -Path $t | Out-Null; Copy-Item "output/{スラッグ}.html" "$t/index.html"; Set-Content "$t/robots.txt" "User-agent: *`nDisallow: /"; npx --yes surge $t --domain "diagram-{スラッグ}-{ランダム6桁}.surge.sh"; Remove-Item -Recurse -Force $t
```

このルートで公開した場合は、`deploy-history.log` に「日時 | URL」を1行追記しておく（削除依頼のときに使うため）。

公開ドメインは `diagram-{スラッグ}-{ランダム6桁}.surge.sh`。Surge は認証なしの完全公開なので、URLの推測しにくさが唯一の防御になる。**ランダム部分を外した固定ドメインで公開しないこと。** URLはスクリプトの出力をそのまま使い、推測で書かない。

原則は確認なしの自動公開でよい。ただし**個人情報・顧客名・未公開の契約内容・社外秘の数字**が含まれる図解だけは、公開前に「誰でも見られるURLになるが公開してよいか」を確認する。

#### 初回（Surge未登録）のとき

メールアドレスとパスワードの入力を求められる。こう伝える:

> 初回だけアカウント登録が必要です。
> メールアドレスを入力して Enter → パスワードを決めて入力して Enter（画面に文字は出ませんが打てています）。
> 新しいメールアドレスなら、それだけでアカウントが自動作成されます。次回からこの手順は不要です。

#### エラーのとき

エラーメッセージをそのまま貼らず、「何が起きていて」「次に何をすればいいか」を平易に説明する。

| 症状 | 対応 |
|---|---|
| `npx: command not found` | Node.js 未導入 → `references/node-install-guide.md` |
| surge 関連エラー | `npm install -g surge` 後に再実行 |
| `Login required` / 認証エラー | `npx surge login` でメール＋パスワードを入力 |
| その他 | エラー全文を読み、原因を1つ特定してから対処する |

### 7. 報告する

公開に成功した場合:

```
完成・公開完了: 【図解のタイトル】

（内容の要約1〜2文）

公開URL:
（スクリプトが出力した実際のURL）

主なポイント:
- （3〜5個）

削除したいときはチャットで「この図解を削除して」と伝えてください。
```

公開できなかった場合は、`output/{スラッグ}.html` の場所と「ブラウザにドラッグ＆ドロップで見られること」「公開したくなったら『この図解を公開して』と言えばよいこと」を伝える。

### 図解の削除を頼まれたら

1. `deploy-history.log` から対象URLを特定する（無ければユーザーに聞く）
2. `npx surge teardown {ドメイン}` を実行する
3. 完了を伝える

## デザインの禁止事項

- **`<style>` タグ・インライン `style` 属性を追加しない** — スタイリングは Tailwind クラスのみ
  - **特にパーセント指定の高さ（`style="height: 20%"`）は絶対に使わない**。Tailwind CDN はクラス名しか処理しないため完全に無視され、画面に「何も描画されない空白」ができる。`h-6`（24px）〜 `h-28`（112px）などの固定高さクラスに換算する
- **`<script>` を追加しない** — テンプレート同梱のもの以外のJSは禁止
- **React・UIフレームワークを使わない** — 静的な図解にフレームワークは不要
- **絵文字を使わない** — OSで表示が変わる。アイコンは Lucide Icons
- **インタラクティブ要素を入れない** — トグル・アニメーション・フォーム・開閉UIは禁止
- **外部リソースを追加しない** — テンプレート同梱CDN以外の画像URL・フォント・CDNは読み込まない
- **額縁を変えない** — `<head>`・CDN読み込み・metaタグはテンプレートのまま
- **PDFで消える表現に注意** — `bg-clip-text text-transparent` のグラデーション文字は印刷時に単色フォールバックになる（テンプレートのprint CSSが対応済み）。使う場合はその前提で

## 内容づくりの原則

- **概論→各論** — 全体像を見せてから詳細へ
- **専門用語は初出で括弧解説** — 「API（ソフトウェア同士がやり取りする窓口）」の形式
- **たとえ話は身近な体験から** — レストランの注文、郵便、信号機など
- **削りすぎない** — 腹落ちに必要な情報量は確保する。要約集にしない
- **図を先に見せる** — 見出しから最初のビジュアルまでテキストは最大2段落。長い説明が要るなら「図→説明」の順にする
- **見たことがあるものは説明せず再現する** — アプリ画面・チャット・ターミナルなど読者が体験済みのUIは、文章で説明する代わりに Tailwind でミニチュアを組んで見せる。「見たことある！」が最強の理解装置
- **冒頭はヒーロー＋一枚絵サマリー** — タイトル → 一言の答え（核心の1文を太字）→ それを図にしたコア図解 → 身近な接点のピル2〜4個 → 「ここから一つずつ解説します」の橋渡し、を一本の流れにする
- **読者のレベルをラベリングしない** — 「初心者向け」「誰でも簡単」等はタイトル・見出し・本文に入れない。わかりやすさは品質で示す
- **ヒーローバッジはトピックのカテゴリ**（テクノロジー、ビジネス、料理など）を入れる
- **日本語で書く** — 英語圏のトピックでも本文は日本語

## ビジュアルの型

ビジュアルは「構造を示す図」と「体験を再現する図」の2種類を組み合わせる。

**構造の図** — 知識の種類で選ぶ:

| 伝えたいこと | 型 |
|---|---|
| Xとは何か（定義） | アナロジー図: たとえの登場人物を配置し矢印で関係を示す。主役は中央に大きく |
| Xはどう動くか（プロセス） | 番号つきステップフロー（横並び、モバイルは縦）。各ステップにアイコン＋一言 |
| XとYの違い（比較） | 左右2カラム対比。同じ観点を同じ行に。✗/✓と赤/緑で差を一目に |
| Xの具体例（事例） | 2列カードグリッド。アイコン＋タイトル＋説明。「表の顔／裏の仕組み」を分けると深みが出る |
| Xのすごさ（数値） | 数字カード3カラム。`text-3xl font-black` で数字を主役に、色は数字ごとに変える |
| Xの中身（階層） | 入れ子ブロック。背景色の濃淡とボーダーで階層を表現 |
| Xの誤解（訂正） | 誤解→正解カード。赤ヘッダーに誤解、本文に緑で正解 |
| Xの変遷（時系列） | 左ボーダーのタイムライン。年号・ラベル・要約 |

**体験の図** — 読者が触ったことのある画面を Tailwind で再現する:

- チャットUI（右寄せユーザー・左寄せAI・入力欄モック）
- エディタUI（赤黄緑ボタン＋ファイルツリー＋コードペイン）
- ターミナルUI（赤黄緑ボタン＋ `$` プロンプト＋出力）
- ブラウザUI（アドレスバー＋ページ内容）
- その他アプリ画面（角丸カード＋アイコン＋数値＋ラベルのミニ再現）

共通ルール: リアルすぎず要点だけ。特定ブランドのロゴ・名称は使わず汎用表現にする。

## 出典の扱い

- **インライン出典** — 採用した事実・数字のすぐ近くに `text-xs text-zu-dim` で小さく「出典: ◯◯公式ドキュメント」形式のリンクを添える。視線の流れを邪魔しない位置に
- **末尾の出典セクション（全図解で必須）** — フッター直前に「出典・情報ソース」を置き、各出典を「**ソース名** ／ 発表: YYYY年M月D日 ／ 取得: YYYY年M月D日」の形でURLリンク付きで列挙する。ユーザー提供資料は「ユーザー提供資料: ◯◯（提供日: …）」とする
- **作成日の明記** — 出典セクション末尾に「**この図解の作成日: YYYY年M月D日**」を太字で置き、「出典側の情報が更新されている可能性があるため、最新の内容は各出典をご確認ください」と小さく添える。図解＝作成日時点のスナップショットだと読者に伝わる
- デザインは `text-sm` で控えめに。主役はあくまで本文の図解
